# LACRA Trace backend: Render deployment runbook (pilot)

Nothing in this repository contains a credential. You enter every secret yourself in the Render, Telnyx, Firebase and
SMTP dashboards. Items marked **[YOU]** need your account. Items marked **[NOT VERIFIED]** are facts taken from
vendor documentation that nobody has exercised against LACRA's accounts yet.

## 1. What `render.yaml` creates

| Resource | Name | Notes |
| --- | --- | --- |
| PostgreSQL 17 | `lacra-trace-pg` | Dedicated to LACRA Trace. Not shared with CMIS or anything else. Paid plan `0.5c-1g`, 15 GB, private network only. |
| Key Value | `lacra-trace-kv` | OTP cache and Celery broker. Plan `starter`, `noeviction`, private network only. |
| Web service | `lacra-trace` | Docker (`Dockerfile`). Runs migrations, creates the admin, collects static files, starts gunicorn. |
| Worker | `lacra-trace-worker` | Docker (`Dockerfile.worker`) running Celery worker **and** beat in one process. Must stay at 1 instance. |

Proposed permanent URL: **`https://lacra-trace.onrender.com`**; API base `https://lacra-trace.onrender.com/api/v1/`.
`lacra-trace.onrender.com` returned `x-render-routing: no-server` when checked from outside, which means no service
holds that name right now. Render only confirms availability when you create the service, so check it in the dashboard.
If it is taken, pick another name and change the five `lacra-trace.onrender.com` occurrences in `render.yaml` before
the first sync (service names cannot be changed later; hostnames follow them). Use a custom domain (for example one
LACRA owns) if you want a URL that never depends on a Render name.

The names are all new on purpose. The earlier `lacra-trace-api` / `lacra-trace-db` blueprint is gone from `render.yaml`,
so applying this one cannot modify an existing service or database.

## 2. Why a worker and a Key Value instance are required

OTP codes are stored in the Django cache (Redis) and delivered by Celery tasks (`send_sms.delay`, `send_email.delay`).
Without the worker no SMS or e-mail is ever sent, so registration cannot complete. The worker also expires transactions
and rolls harvest seasons forward (beat).

## 4. Step-by-step

1. **[YOU]** Render dashboard: *New > Blueprint*, connect `DevKonneh/lacra-trace-backend`, pick the reviewed branch
   (do not deploy `main` until PR #1 is merged; `main` still holds the old free-tier blueprint).
2. **[YOU]** Enter the prompted values from section 3. Apply.
3. First deploy runs `migrate` (default and `test_mode` schema), creates the admin and starts gunicorn. The worker may
   crash-restart once or twice on the very first deploy while the web service is still creating the `django_celery_beat`
   tables; it recovers on its own.
4. Check `https://<host>/api/v1/system/healthcheck/` returns 200 and `https://<host>/admin/` shows the LACRA login.
5. **[YOU]** Firebase (section 7), then flip `PUSH_NOTIFICATIONS_FCM_ENABLED` to `True` on both services.
6. Tell us the final host. The Android APK is built against `https://<host>/api/v1/` and `https://<host>/api/v1/test/`.

## 5. Telnyx (SMS / OTP to Liberia) **[YOU]**

* Create/verify the Telnyx account, create a **Messaging Profile**, copy its ID and an API v2 key.
* Liberian traffic: Telnyx documents that alphanumeric sender IDs are supported but that Lonestar MTN (MCC/MNC 61801)
  requires sender registration, otherwise the sender is overwritten or the message is not delivered. Orange Liberia
  behaviour is **[NOT VERIFIED]**. Contact Telnyx (`alpha_sender_id@telnyx.com`) to register the sender ID LACRA wants
  before the pilot, and confirm both carriers in a real test. Do not assume delivery.
* Phone numbers are sent to Telnyx as `+` followed by digits (`+231...`), see `normalize_phone` in
  `lacra/common/validators/auth.py`.

## 6. SMTP and S3 **[YOU]**

* Render **blocks outbound SMTP on ports 25, 465 and 587 for free web services**; the plans in this blueprint are paid,
  but use a provider that offers port 2525 or 587 over TLS with an authenticated domain. The blueprint defaults to 2525;
  change `EMAIL_PORT` if your provider differs.
* S3: any S3-compatible bucket (AWS S3, Cloudflare R2, Backblaze B2, MinIO). Create a private bucket and a key limited
  to it. Render itself has no object storage.

## 7. Firebase **[YOU]** (push notifications only; registration/login/transactions do not depend on it)

1. In the Firebase console use the project that is (or will be) registered for the Android package
   `lr.gov.lacra.trace` (debug builds use `lr.gov.lacra.trace.dev`; add both apps to the project).
2. Project settings > Service accounts > *Generate new private key* (JSON).
3. Render: on **both** `lacra-trace` and `lacra-trace-worker`: *Environment > Secret Files > Add*, filename `fcm.json`,
   paste/upload the JSON. It is mounted at `/etc/secrets/fcm.json`, which is what `PUSH_NOTIFICATIONS_FCM_CREDENTIALS_PATH`
   points to. Secret Files are limited to 1 MB total per service.
4. Set `PUSH_NOTIFICATIONS_FCM_ENABLED=True` on both services and redeploy.
5. Android side (separate PR): put the `google-services.json` for the same Firebase project in `app/`
   (git-ignored; never committed).

Never commit the service-account JSON or `google-services.json`.

## 8. Database: migrating existing data safely

A pre-existing Render database for LACRA Trace could not be inspected from the build environment (it needs your Render
login). Decision tree:

* **No database / no real records** (most likely: the earlier blueprint never went live, and a free instance would have
  expired): nothing to migrate. This blueprint creates a fresh, dedicated `lacra-trace-pg`.
* **A database with real records exists:**
  1. Back it up first, from a trusted machine, with the **external** connection string from the Render dashboard:
     `pg_dump --format=custom --no-owner --file=lacra_pre_migration_$(date +%F).dump "$EXTERNAL_DATABASE_URL"`
     (free instances have no Render-side backups; free instances also expire 30 days after creation and are deleted
     after a 14-day grace period). Store the dump somewhere outside Render.
  2. Restore the dump into a scratch Postgres 17 and run `./manage.py migrate` there first.
  3. Only then point a deploy at the real database.

### How old `Season` records move to the harvest-season model (tested on synthetic data only)

The migration chain `0005`-`0020` was run against a database built from the legacy (pre-harvest-season) schema with
synthetic rows (not real LACRA data). Findings:

* `0010` raises `RuntimeError: N commodity dates are not covered by any harvest season` if a transaction/commodity has a
  date outside every season. Fix before migrating: create seasons covering the earliest transaction date.
* `0017` fails with `UniqueViolation ... harvest_season_group_single_past` if a covering season is `past` while another
  `past` season exists in the same group. Creating the extra covering season as `archived` allowed the chain to finish
  through `0020`.
* The old `Season` name and description text are not carried into the new model.
* After migration: confirm with LACRA the real season calendar (spans of 6 or 12 months, one group per season) before
  production use.

Because only synthetic data was available, this demonstrates the failure modes and a working path; it is not a
guarantee for real records. Run the dry run on a copy of the real dump.

## 9. Operations

* Backups: use a paid Postgres plan (Render documents backups/point-in-time recovery for paid instances; check the retention for your workspace plan, restore not exercised) and also take periodic external `pg_dump`
  files. Restore is untested.
* To reach the database from your machine for a backup, temporarily add your IP to the database's allow-list in the
  dashboard (the blueprint ships an empty list = private network only), then remove it.
* Auto-deploy is `off` for web and worker: deploy manually after PR review.
* Scaling: keep `lacra-trace-worker` at 1 instance (it also runs beat).
* Worker + beat share one process to keep the pilot at one extra service. If you later scale the worker, split beat out
  using `Dockerfile.beat` as a separate worker service.
